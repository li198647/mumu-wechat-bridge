| 判据 | 实测 |
|---|---|
| 主窗口类名 | `Qt51514QWindowIcon`（**不是** `mmui::MainWindow`）896×648 title='微信' |
| 子窗口 | `MMUIRenderSubWindowHW` 880×640（真界面画在这里面） |

| 标题含「文件传输助手」的独立窗口 | 无 |

**结论：微信 4.x 的 UIA 控件树在本机（4.1.15.13）读不出来** —— 属已知的

本机 DPI/多屏这两个常见诱因已排除（96 / 单屏）。社区那批"4.1.12.55 可用"的记录不适用于此版本。

→ 因此**驱动 PC 微信（类 wxauto）这条路**：路线甲（UIA 控件树）✗ 已实测否决；
路线乙（靠"标题带会话名的独立窗口"做免控件树键盘流）本机也没有该窗口。

## 2026-10-09 22:20 登录环节落地（`tools/login_web.py`）

**通道实测确认**：`https://filehelper.weixin.qq.com/` 在 **headless 下完全正常**，
标题 `微信文件传输助手网页版`；未登录时页面只有一个二维码：

- 二维码载体 = **`<img>` 元素**，160×160，`src=https://login.weixin.qq.com/qrcode/<uuid>==`
  （不是 canvas、不是 iframe，选择器直接抓 `img[src*=qrcode]` 即可）
- 登录判据**不能**用文本含『文件传输助手』——**登录前页面文案里就有这五个字**，会误判。
  可靠判据：① 二维码 img 还在 ⇒ 必然未登录；② 出现 `textarea/[contenteditable]/#chat-input` ⇒ 已登录。

**登录态载体**：Playwright `launch_persistent_context(user_data_dir=tools/.wxprofile)`，
cookie 落在 `.wxprofile/Default/`，之后发送端复用同一 profile 即可免扫码。

**本机踩坑（重要，写脚本必看）**
1. `run_in_background=true` 或 `timeout=` 参数 + 命令里带 `; echo ...` 会触发沙箱层报错
   `sandbox-center cmd decisionRecord missing actual resource subject`（试了 3 次都被拒）。
   **解法**：命令结尾带 `2>&1`（或 `2>&1 | tail -N`）即可正常执行。
2. `nohup python xxx.py &` 起的后台进程**活不下来**（日志停在启动头，无后续输出）。
   **解法**：用工具自带的 `run_in_background=true`，并带 `2>&1`。
3. 脚本日志必须**实时落盘**（每次 log 都重写 report 文件），否则进程被回收后拿不到中间进度。
4. 二维码会过期；脚本目前每 2.5s 重截一次到 `wx_qr.png`，但**没有"过期后重载页面"的逻辑**，
   若超时需人工重跑或补一段 reload。

**本次产物**：`tools/login_web.py`（`--probe` 探测 / 默认登录 / `--headed` 有界面 / `--wait N` 等待秒数）、
`tools/wx_qr.png`（二维码原图）、`tools/wx_qr_big.png`（3 倍放大便于手机扫）、`tools/login_report.txt`（实时日志）。

### 22:32 重大发现：网页版登录态「关浏览器就丢」，桥改常驻形态

**事实链**
1. 22:30 木木实际扫码**成功**了（当时页面只是显示"二维码已失效"误导了他）。截图证据
   `tools/wx_after_login.png`：标题「小林的传输助手」、底部输入框 + 「发送」按钮、空消息区。
   ⚠️ 记住：**登录后页面标题形如「<微信昵称>的传输助手」**，不是"文件传输助手"。
2. 但 **22:31 重开浏览器（同一 profile）又回到未登录**，cookie 没保住。逐层排查：
   - `Default/Network/Cookies` 里有 9 条：`webwx_auth_ticket`、`wxsid`、`wxuin`、
     `wxpluginkey`、`wxloadtime`、`webwxuvid`、`webwx_data_ticket`、`mm_lang`
   - **全部挂在 `.szfilehelper.weixin.qq.com` 域下**（不是我访问的 `filehelper.weixin.qq.com`）
   - 都是 `is_persistent=1`（不是会话 cookie），`expires_utc` 也在未来
   - 但 **`encrypted_value` 长度 = 0 → 值没真正落盘**
   - `Default/Local Storage/leveldb` 里 `webUin` 等**倒是持久化成功了**（filehelper 与 szfilehelper 两个域都有）
3. ⇒ 结论：**官方网页版的登录会话天生不安分，不能指望"存 cookie、下次免扫"。**

**设计对策（重要）**：桥本来就是常驻形态（浏览器一直开着 ⇒ 会话一直活着），
所以不纠结"重开免扫"，改按**常驻服务**做：
`login_web.py` 升级为 `--serve` 模式——扫码成功后**浏览器不关**，进入待命循环，
轮询 `tools/send_cmd.txt`：普通文本 ⇒ 发给文件传输助手并把结果写 `tools/send_result.txt`；
`__probe__` ⇒ 重新 dump 控件到 `tools/chat_dom.txt`。
**这样木木只扫一次码，我就能反复实测发送，不用反复扫码。**
登录成功还会顺手导出 `tools/state.json`（`ctx.storage_state()`）作为凭证快照备用。

### 22:40 架构定为「独立浏览器 + CDP 解耦」

**又两个实测结论（都推翻了前一轮的猜测）**
1. **cookie 快照救不回登录**：把 `state.json` 里的 9 条明文 cookie（含 `webwx_auth_ticket` /
   `wxsid` / `wxuin`）+ localStorage 用 `ctx.add_cookies` / `add_init_script` 注入后，
   页面**依然显示二维码**。⇒ 微信网页版的会话与「浏览器进程是否活着」强绑定，
   浏览器一关服务端就注销 session。**不是 profile 落盘问题，是服务端行为。**
2. **`send_message` 第一版失败**：找到 textarea 并填了字，但点的是外层容器
   `div.chat-panel__input-send`（550×64），不是真按钮；消息没发出去。
   真按钮是 **`a.chat-send__button`**（未输入文字时带 `chat-send__button__disabled`）。
   ⚠️ 另外：Chrome 的 `document.body.innerText` **不含 textarea 的值**，
   所以"body 文本里看不到刚填的字"是正常的，不能据此判定没填进去。

**定稿架构（解决"改一次代码就要扫一次码"）**
```
独立常驻 Chromium（--remote-debugging-port=9222，DETACHED_PROCESS）
        ↑ connect_over_cdp
桥脚本 login_web.py（可随意重启）
```
- 浏览器用 `p.chromium.executable_path` 直接 Popen 拉起，
  路径 `C:\Users\Administrator\AppData\Local\ms-playwright\chromium-1234\chrome-win64\chrome.exe`
- 桥脚本 `connect_over_cdp("http://127.0.0.1:9222")` 接上去干活；实测连接耗时 **0.7s**，正常
- **踩坑：CDP 连上的 context 上调用 `ctx.add_init_script()` / `ctx.add_cookies()` 会挂死**
  （第一版卡在"独立浏览器已就绪"之后无任何输出）。
  干脆两个都去掉——stealth 实测不需要，cookie 注入已证明无效。
- 重启桥脚本时浏览器若仍活着，`ensure_browser()` 会**复用**它，登录态不受影响

**坑 1：Ctrl+Alt+S 在本机已被别的软件占用**
`RegisterHotKey` 返回错误码 **1409 = ERROR_HOTKEY_ALREADY_REGISTERED**。
⇒ 改成**候选列表依次重试**：`Ctrl+Alt+S → Q → D → X → A`，第一个成功的就用；
实际热键名通过 `tray.hotkey_name` 暴露，日志/气泡里都会说明。
（`HOTKEY_CANDIDATES` 就在 wx_tray.py 顶部，日后想加直接改。）

**坑 2（决定性）：TaskStop 会诛九族，连"分离"过的子进程也不放过**
- 实测：停掉拉起浏览器的脚本后，`9222` 端口消失、`chrome.exe` 进程数归零。
- 加了 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` **无效**；
  再加 `CREATE_BREAKAWAY_FROM_JOB (0x01000000)`（且 Popen 没报错，说明标志被接受）**依然无效**。
- ⇒ **凡是由自动化工具启动的进程，都会被连带清理。**

**最终架构（绕开上面这个坑）**

### 23:15 热键定案：改用 Ctrl+Alt+数字

**代码改动**
1. `wx_tray.py`
   - `HOTKEY_CANDIDATES` 改为：**Ctrl+Alt+数字 1~9、0 → 小键盘数字 → Ctrl+Shift+Alt+数字**。
   - 🔴 **修了一个真 bug**：之前用 `ctypes.windll.user32` 调 `RegisterHotKey`，
     而 **windll 不保存 last error，`ctypes.get_last_error()` 永远返回 0** ——
     所以"被占用"这个结论其实是猜的（错误码 1400 句柄无效也会被报成"被占用"）。

2. `wx_bridge.py`：新增 `on_scan()`，托盘点「热键检测」→ 逐条写日志 + 气泡简报可用组合。

**注意**：热键是**全局资源**，桥自己占着的那个在检测里会显示为"被占用"，属正常。
